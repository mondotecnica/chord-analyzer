# コード解析アプリ — Phase 0 試作

音楽のオーディオファイルからコード進行を解析する Web アプリの試作（Phase 0）です。

**設計の原則**

- 音声ファイルは **ブラウザ内でのみ処理** し、サーバーへアップロード・保存することは一切ありません（書き出しファイルにも音声は含まれません）。
- バックエンドなしの静的サイトとして動作し、運用コストはゼロを目標にしています。
- まずは自分用、将来的に一般公開を想定しています。
- UI はモノクローム基調＋アクセント1色、余白とタイポグラフィで構成するデザイン方針です（ライト／ダーク両対応）。音声を読み込むと、再生／一時停止・現在のコード・再生位置が画面下部に固定表示されます。

## 動かし方

```bash
npm install
npm run dev      # 開発サーバー（表示された URL をブラウザで開く）
npm run build    # 本番ビルド（dist/ に出力）
npm run preview  # ビルド結果のプレビュー
npm test         # ユニットテスト（vitest）
```

## 使い方

1. 音声ファイル（mp3 / wav / m4a / ogg / flac など、ブラウザがデコードできる形式）をドラッグ＆ドロップするか、「ファイルを選ぶ」から選択します。
2. 自動で解析が始まり、キー（推定）、BPM（推定）、コードセグメントが表示されます。
3. 再生するとタイムラインと一覧の現在コードがハイライトされます。セグメントをクリックするとその位置へシークします。再生コントロールは画面下部に固定表示されるため、スクロール中でもいつでも一時停止できます。
4. セグメントのコードはセレクタで手動修正できます（12ルート × メジャー／マイナー + N.C.）。修正した結果も書き出しに反映されます。
5. 「JSONで書き出し」「テキスト譜で書き出し」から結果をダウンロードできます。

## GitHub Pages への公開

カスタムドメインは不要で、GitHub の無料サブドメイン
`https://<ユーザー名>.github.io/<リポジトリ名>/` でテスト公開できます。

手順（リポジトリ作成後に一度だけ）:

1. GitHub でリポジトリを作成し、このプロジェクトを push する
   （`git remote add origin ...` → `git push -u origin main`）。
2. リポジトリの **Settings → Pages → Build and deployment → Source** で
   **GitHub Actions** を選ぶ（この設定はワークフロー側からは変更できない）。
3. 以後は `main` への push（または Actions 画面からの手動実行）で
   `.github/workflows/deploy-pages.yml` が `npm ci` → `npm run build` →
   `dist/` の公開まで自動で行う。

ビルド時の注意:

- Vite の base は相対 (`./`) が既定（`vite.config.ts`）。サブパス配置でも
  JS/CSS・分離 Worker・onnxruntime-web の WASM がすべて相対参照で
  解決されるため、リポジトリ名に依存せず同一ビルドが動きます。
  固定サブパスに置きたい場合のみ `VITE_BASE_PATH=/<repo>/ npm run build`
  のように環境変数で上書きできます。
- 高精度モードの分離モデル（約172MB）はアプリに同梱せず、従来通り
  Hugging Face CDN から取得します（Pages の転送量を圧迫しません）。

## アーキテクチャ

処理はすべてクライアントサイドで、段階ごとにモジュールを分離しています（後フェーズで差し替え・追加がしやすい構成）。

```
src/
  audio/loadAudio.ts        Web Audio API でデコード＋モノラル化、再生用オブジェクトURL
  dsp/fft.ts                自前 FFT（基数2）と Hann 窓
  dsp/chroma.ts             STFT → クロマグラム（HPCP風, FFT 4096 / hop 2048）＋オンセット包絡
  analysis/chordEstimation.ts  コードテンプレート（major/minor）とのコサイン類似度マッチング、信頼度、N.C.判定
  analysis/keyTempo.ts      キー推定（Krumhansl–Schmuckler）／テンポ推定（オンセット自己相関）
  analysis/segmentation.ts  メディアン平滑化 → セグメント化 → 短セグメント吸収
  analysis/analyze.ts       パイプライン統括（進捗通知つき）
  analysis/exportResult.ts  JSON / テキスト譜への書き出し
  lib/notes.ts              音名・コード名・時刻フォーマット
  components/Timeline.tsx   再生同期タイムライン
  components/SegmentList.tsx セグメント一覧＋手動修正セレクタ
  App.tsx                   画面全体（入力、プレイヤー、結果表示）
```

当初候補だった Essentia.js（WASM）は、Vite との統合の壊れやすさを避けるため Phase 0 では採用せず、同等の処理（STFT クロマ＋テンプレートマッチング＋キー／テンポ推定）を自前 TypeScript で実装しています。モジュール境界は揃えてあるので、必要になれば後から差し替えできます。

## Phase 0 の制限（正直なところ）

- 対象コードは **メジャー／マイナーの三和音のみ**（7th、テンション、sus、dim、aug などは未対応）。
- **ステム分離なし**：フルミックスをそのまま解析するため、ボーカルのメロディやドラムの影響で誤判定が起こります。これが既存アプリの精度限界でもあり、本プロジェクトが後フェーズで取り組む課題です。
- キーと BPM は簡易な推定であり、特に BPM はオクターブ違い（半分／2倍）になる場合があります。
- **精度はまだ検証していません**。手動修正と JSON 書き出しは、正解コード譜と突き合わせて正解率を測るための土台です。
- 長い曲では解析に時間がかかり、スマートフォンではメモリ不足になる場合があります。まず短めの曲でお試しください。

## ロードマップ

- **Phase 0（本試作）**: ステムなし試作＋正解率測定の土台
- **Phase 1**: ベース帯域の解析によるルート補正（実装済み。現在の解析の既定は Phase 1.5 の帯域分業＝ルートは全帯域＋ベース補正／モードは上帯域 260Hz で決め直す構成。2026-10-27 に実曲 3 曲の総括を受けて既定化。詳細は measurements/PHASE1_SUMMARY.md）
- **Phase 2**: Demucs 分離（ONNX / WebGPU、PC向け高精度モードとして任意ON）
- **Phase 3**: 7th／テンション拡張＋ジャンル解析の傾向を事前分布として活用

将来の公開形態として Firebase Hosting（＋必要に応じて Firebase Auth）への配置を想定していますが、Phase 0 では未接続です。
