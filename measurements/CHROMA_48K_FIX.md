# 48kHz クロマ異常の修正と検証（解析レート統一・方式 (a)）

> 対象: SUNO_YOI_ANALYSIS.md の診断で判明した「48kHz 入力でプロジェクトの
> クロマが低域の音高クラスを半音側へ回す」異常への対策。オーナー承認済み
> 課題（2026-10-29）。本書は実施前に登録した検証基準を冒頭に転記し、
> その基準で判定する。push はしていない（公開判断はオーナー）。

## 事前登録した検証基準（実施前に登録・そのまま転記）

1. **不変性**: 44.1kHz 入力に対する全既存スイート（合成曲 A〜I の混合音・
   ステム、実曲1〜3、Suno 05 の両経路、宵のひかり A44/B）の結果が修正前と
   ビット一致（または完全一致）すること。一致しない場合は差分の原因を
   特定して報告し、勝手に「許容」としない
2. **正常化**: 48kHz 入力で (i) 合成 Am/C の診断トーンが正しいキー・
   音高クラスで読めること、(ii) 05@48kHz が A# minor でなく A minor と
   読めること、(iii) 宵のひかりの 48kHz 混合音解析が A44 とキー一致し、
   セグメント三和音一致率が A44–B 間と同水準（3割前後）以上に回復すること
3. **他レート**: 可能なら 32kHz / 96kHz の診断トーンでも同様に正常化
   されること（入口統一なら自動的に満たされるはず、その確認）
4. **回帰**: 全テスト合格。パフォーマンス面で解析時間が露骨に悪化
   しないこと（リサンプル追加の影響を一言でよいので計測）

## 診断の要約

プロジェクトのクロマ（src/dsp/chroma.ts）は FFT 4096 点で各ビンを
最近傍の音高クラスへ割り当て、低域ほど重みを大きくする
（`1/(1+log2(f/50)*0.35)`）。48kHz では低域のビン間隔
（48000/4096 ≈ 11.7Hz）が半音間隔より粗く、110Hz 付近に「A に
丸められるビン中心」が存在しないため、A2 のエネルギーが G#/A# 側の
ビンへ落ち、低域重みがそれを増幅する。44.1kHz はビン格子と音名格子の
当たりが偶然良いだけで、原理的な保証はない。証拠は
SUNO_YOI_ANALYSIS.md 診断節: 合成 Am 三和音が 48kHz で C# minor に
誤読（自前 FFT 8192 点クロマでは正常）、05 を正しく 48kHz 化した版も
A# minor 誤読。

製品への影響: 簡易モード（混合音経路）はブラウザの AudioContext の
デコードレート（多くの PC / Android で 48kHz）をそのまま解析へ渡して
いたため、公開中の簡易モードがこの劣化に晒されていた。高精度モードは
分離前に 44.1kHz へリサンプルする設計で、影響を受けていなかった
（コード確認: App.tsx が resampleStereo / resampleChannel で
SEPARATION_SAMPLE_RATE=44100 に揃えてから analyzeStemsAudio を呼ぶ）。

## 修正内容（方式 (a): 解析の入口で 44.1kHz に統一）

推定器（クロマ）自体は一切変えていない。全ての較正基準が現行クロマで
取られているためである。変えたのは「解析に渡るサンプルレートの
正規化」だけであり、製品の既定（モード、bandStrategy、ゲート等）は
不変。

| ファイル | 変更 | 理由 |
|---|---|---|
| `src/analysis/sampleRate.ts`（新規） | `ANALYSIS_SAMPLE_RATE = 44100` と `normalizeToAnalysisRate()`。44.1kHz 入力では同一配列をそのまま返し、それ以外は既存の線形補間リサンプル（`src/stems/audioPrep.ts` の `resampleChannel`、高精度経路が従来から使う手段）を適用する | 正規化の単一の置き場。44.1kHz で無変換であることが不変性（基準1）の機構的な担保になる |
| `src/analysis/analyze.ts` | `analyzeAudio` の入口で混合音を正規化。以後の処理と結果の `sampleRate` は実効レート（44100）を使う | 簡易モードの入口。App.tsx はここを通るため、アプリ側の変更は不要になった |
| `src/analysis/analyzeStems.ts` | `prepareStemChromas` で mix / other / bass と追加ステム（drums / vocals）を全て正規化。`StemChromas.sampleRate`（実効レート）を追加し、`analyzeWithStems` / `analyzeStemsAudio` はそれを結果へ渡す | ステム経路のクロマ計算は全てこの関数を通る（製品入口・全測定ハーネスの共通の急所）。mix 参照（キー／テンポ／ゲート参照）もここで揃う |
| `src/analysis/sampleRate.test.ts`（新規） | 恒常テスト 11 件: 正規化の単体（44.1k 無変換の同一参照、48k→44.1k の長さ）、入口越しの診断トーン（Am/C × 32k/44.1k/48k/96k → キーと支配セグメント）、ステム入口 @48k | 異常の再発防止。診断用スクリプト（scripts/suno-yoi-diagnostic*）は生クロマを直接叩く一回限り診断として残置（下記「残存リスク」参照） |
| `scripts/measureSunoYoi.ts` / `scripts/measure-suno-yoi.test.ts` | アーム C44 を追加（§副次測定）。他のハーネスは入口共通化により変更不要だった | C の交絡切り分け |

入口の洗い出し結果: 製品の解析入口は `analyzeAudio`（簡易）と
`analyzeStemsAudio`（高精度）の2つで、後者のクロマは
`prepareStemChromas` 経由。測定ハーネスも同じ2入口＋
`prepareStemChromas`+`analyzeStemsWithStrategy` の直接利用のみで、
44.1kHz 以外を流すのは宵のひかり測定（48kHz）だけだった。
`computeChromagram` を直接叩くのは診断スクリプトのみで、これは
意図的に未変更（推定器の SR 依存そのものは残る、方式 (b) の領域）。

## 検証1: 不変性（基準1）

方法: 修正前に全スイート（`npm test`、402 件合格＋1 スキップ）を
実行して measurements/ ツリー全体をベースラインとして保存し、
修正後に再実行してツリー全体を再帰 diff した。

結果: **差分が出たのは `measurements/suno-yoi-results.json` のみ**。
合成曲 A〜I（混合音・ステム）、実曲1〜3、Suno 05 の両経路、
phase1/2/3・nc・notepitch・genre・meter の全 JSON/MD、
test-audio の正解 JSON はすべてビット一致した。唯一差分のあった
suno-yoi-results.json の内部でも、44.1kHz 入力のアームは完全一致を
確認した:

- アーム A44 の要約（diagnostics.a44MixtureSummary）: 完全一致
- アーム B（キー・N.C. 6.9%・157 セグメント・信頼度 0.635・全セグメント）: 完全一致
- フィクスチャ B: 完全一致。アーム間一致率 A44–B（33.4 / 29.7 / 21.4）: 完全一致
- 参考アーム（05 mixture / stems の要約）: 完全一致
  （`vsArmC_0to205` だけは相手のアーム C 自体が変わるため変動し、
  全項目で改善: 三和音 vs refStems 41.6 → 52.5 等）

差分が残るのは 48kHz 入力のアーム A / C / D と診断プローブ
（srProbe の 05@48k 等）で、いずれも本修正の対象そのもの。
44.1kHz 入力に対する差分はゼロであり、基準1は合格。

## 検証2: 正常化（基準2）

(i) **合成トーン**: 恒常テスト（sampleRate.test.ts）で、Am / C の
診断トーン（純正弦波＋弱い倍音、診断2と同じ作り）を 48kHz で
`analyzeAudio` に通し、キー（A minor / C major）と支配セグメント
（Am / C）が正しく読めることを固定した。なお診断スクリプトの
生クロマプローブ（computeChromagram 直接）は 48kHz で従来どおり
C# minor を返す。推定器を変えていない以上これは設計どおりで、
保証は「解析入口越し」に置く（恒常テストも入口越しに書いてある）。

(ii) **05@48kHz**: `analyzeAudio` のキーが A# minor → **A minor** に
回復。支配ルートも A#:29s / G:29s / F#m:20s / C#m:19s という
+1 半音の世界から、Am:68s / G:41s / D:27s / Bm:18s（44.1kHz 版と
同系）になった（suno-yoi-results.json の diagnostics.srProbe）。

(iii) **宵のひかり 48kHz 混合音（アーム A）**: キー A# minor →
**A minor**（A44 と一致）。要約値も A44 と完全一致した
（N.C. 9.9% → 8.9%、信頼度 0.596 → 0.614、セグメント 102 → 121、
いずれも A44 の値そのもの）。一致率では A–A44 三和音 99.5%、
**A–B 三和音 29.7%** で、基準が参照する A44–B の 29.7% と同値まで
回復した（修正前 A–B は 15.5%）。基準2は (i)(ii)(iii) とも合格。

## 検証3: 他レート（基準3）

恒常テストで 32kHz / 96kHz（および 44.1kHz / 48kHz）の Am / C
トーンを入口越しに検証し、全レートでキーと支配セグメントが
正しく読めることを固定した。入口統一の帰結どおり、レートに
よらない読みになった。

## 検証4: 回帰と性能（基準4）

- 全テスト: **413 件合格＋1 スキップ**（修正前 402 件＋1 スキップ、
  差分 +11 は新規恒常テスト）。失敗ゼロ。`npm run build` 成功
- 性能（この VM で計測）: 212.8 秒・48kHz の合計ミックスに対する
  リサンプル単体は約 145ms。`analyzeAudio` 全体では 48kHz 入力
  （リサンプル込み）1271ms vs 44.1kHz 入力 1033ms で、追加コストは
  213 秒の曲あたり約 +0.24 秒。解析時間の露骨な悪化はない

## 副次測定: アーム C の交絡切り分け（要約）

Suno 9ステムを ffmpeg で 44.1kHz 化して C と同じ写像で解析する
アーム C44 を追加し、48kHz 版 C（修正前）・修正後の C（入口で
線形補間リサンプル）と並べた。C44 と修正後 C の一致率は三和音
99.0% で、リサンプラの違いは読みにほぼ影響しない。

48kHz 要因で説明できたもの: 見出しキーの誤り（解消）、信頼度の
差（0.580 → 0.632、B の 0.635 とほぼ解消）、B との一致率
（三和音 44.3 → 60.7）、Q2 の Cm 時間（5.95 → 3.65 秒）。
**説明できなかったもの**: N.C. 率の差（11.9 → 11.3〜11.6%、
B は 6.9% でほぼ不変）、Q1 のベース（前半は F#→G で依然誤り、
後半は D→A と正解から外れた）、Q4 の表示（Em のまま、
決着 CM7/C# は再現せず）、Q2 の Cm 残存（3.65 秒、B は 1.05 秒）、
Q3 の最終スライス（Am → C へ後退し 4/4 → 3/4）。

結論: **C の不利の主因はサンプルレートではなく、製品のステム経路が
mix / other / bass しか消費しない構造と、この曲の和声ステムが
全エネルギーの約 4% しかない編成にある**、という元の解釈が、
交絡を除いた再測でも維持された。SUNO_YOI_ANALYSIS.md の結論
（精度では Demucs 経路が同等以上、直接入力の価値はワークフロー）
は書き換え不要で、詳細は同書の追記に残した。

## 方式 (b) の見通し（今回は実装しない）

クロマ自体を直すなら、低域でのビン割当てを率ロバストにするのが
本筋である。候補: (1) 最近傍割当てを周波数重みつき（補間）配分に
変える、(2) 低域だけ長い窓（多重解像度 STFT）や CQT 的な対数
周波数軸にして、低域でもビン間隔が半音以下に収まるようにする、
(3) 低域重み曲線の見直し。いずれも全フレームのクロマ値が変わる
ため、較正の土台（合成 A〜I・実曲1〜3・Suno フィクスチャ、ゲート
閾値、第2段や層表示の各閾値）を全て測り直す必要がある。測定
ハーネス一式は揃っているので実行自体は可能だが、計算に数時間
規模＋各測定文書の採用判定のやり直しが伴う。本修正（方式 (a)）は
その再較正コストなしに、公開中の簡易モードの劣化という実害を
止めるためのもので、(b) は「推定器を世代交代させる」別課題として
切り分けるのが妥当である。

## 残存リスク

- **生クロマの SR 依存は残っている**: `computeChromagram` に
  44.1kHz 以外を直接渡す新しい経路を作ると異常が再発する。
  解析は必ず `analyzeAudio` / `prepareStemChromas` を通すこと
  （sampleRate.ts のコメントにも明記）。診断スクリプト
  （scripts/suno-yoi-diagnostic*）はその切り分け用に生クロマを
  叩き続けるため、その出力の読みには注意が要る
- **線形補間リサンプルの品質**: アンチエイリアスを持たない簡易
  リサンプルだが、実測では ffmpeg リサンプル版との一致率が
  三和音 99.0%（アーム C/C44）、混合音でも A–A44 が 99.5% で、
  読みへの影響は無視できる範囲だった。高品質リサンプラへの
  差し替えは 48kHz 入力の結果を僅かに変えうる（44.1kHz の
  不変性には影響しない）
- **二重リサンプル**: ブラウザの decodeAudioData はファイルを
  コンテキストレートへ変換するため、例えば 22.05kHz のファイルは
  48kHz 経由で 44.1kHz 解析になる。読みの正しさは保たれるが、
  音質的には一段余分な変換が入る（解析用途では許容範囲と判断）
- 05@48k の検証素材は 44.1kHz 原版からの正しいリサンプルであり、
  48kHz ネイティブ収録の実素材そのものではない。ただし異常の
  機構はレート由来で内容非依存であり、4 レートの合成トーンで
  原理は担保している

## 再現手順

1. 不変性: 修正前 HEAD で `npm test` → `measurements/` を退避 →
   修正後 `npm test` → ツリーを再帰 diff（差分は
   suno-yoi-results.json のみ、その内部の A44 / B は完全一致）
2. 正常化・他レート: `npx vitest run src/analysis/sampleRate.test.ts`
3. 宵のひかり再測（C44 含む）: 素材の用意は SUNO_YOI_ANALYSIS.md
   追記の手順を参照し、`npm run measure:suno-yoi`
