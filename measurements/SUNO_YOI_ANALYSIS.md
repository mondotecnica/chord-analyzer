# Suno 自作曲「宵のひかり」ステム直接入力の検証（正解譜なし・比較測定）

> **対象曲**: 「宵のひかり（= 05.mp3 と同一曲、05 は末尾の短い本人ミックス版）」。
> ユーザーが Suno から書き出した 9 ステム（Vocals / Backing Vocals / Bass /
> Drums / Guitar / Keyboard / Synth / Strings / FX）を材料に、
> 「Suno ステムを直接入力する経路は、Demucs 分離を経由する現行の高精度
> モードより良い解析になるか」を測った。
> 同一曲であることの確認（別途検証済み）: 05.mp3（205.14 秒）とステム合計
> （212.80 秒）のクロマグラム相関は全ラグ走査でラグ +0.1 秒（実質ゼロ）に
> 平均コサイン類似度 0.982。長さの差 約7.7 秒は末尾側にあり、開始位置は
> 一致する。05 はユーザーが Logic でミックスした版であり、ステム素の
> 合計とはバランスが異なる**別物**として扱う（本書では「参考アーム」）。
>
> **この曲にも公式コード譜は存在しない。したがって本書も正解率は一切
> 出していない。** 評価は (1) アーム間の比較指標、(2) 05 でユーザーの
> 耳チェックと音響証拠により決着済みのフィクスチャ Q1〜Q4（オフセット
> ≒0 のため同じ時刻にそのまま適用できる）、の2系統で行う。
> 生データは [suno-yoi-results.json](suno-yoi-results.json)。

## ファイル事実と手法

- 入力: 9 ステムの MP3（各 212.80 秒・48kHz ステレオ・320kbps 相当）。
ユーザーの手元 WAV（1トラック 40MB 超）がアップロード制限のため
MP3 化されたもの。**MP3 変換経由であることが本測定の制約**（特に
ステム品質の細部はロスレスではない前提で読むこと）
- 前処理: ffmpeg で 16bit WAV にデコード（stem-work/suno-yoi/src/）。
9ステムを float で合計するとピーク 1.257（フルスケール超過サンプル
0.0012%）に達したため、合計ミックスはゲイン 0.795（−2.0dB）を掛けて
正規化した（prep-info.json に記録）。グループ合計（other 等）も同じ
ゲインを適用し、追加の正規化は不要だった
- Demucs: ローカル HTDemucs（torch 版）で合計ミックスを分離
（255 秒／ピーク RSS 1.7GB、出力 44.1kHz）。公開アプリの ONNX 版と
モデル系は同じで解析コードは同一
- 解析は全て現行製品既定のまま（混合音 = split、ステム = s-conditional、
フレームゲート = song-referenced、層表示 ON、局所キー記録 ON、
第2段拡張は OFF）。解析時点のコード: git HEAD `b151ee7` 系
（測定ハーネスの追加のみで製品コードは無変更）
- ハーネス: scripts/measureSunoYoi.ts（`npm run measure:suno-yoi`）、
ステム品質: scripts/sunoYoiStemQuality.py

## アーム定義

| アーム | 内容 |
|---|---|
| A 混合音（48kHz） | 9ステム合計ミックスを `analyzeAudio`（製品既定）で解析。**後述の 48kHz クロマ異常の影響下にあり、比較の本線からは外す** |
| A44 混合音（44.1kHz） | 同じ合計ミックスを 44.1kHz にして混合音解析。混合音経路の代表はこちら |
| B Demucs 経路 | 合計ミックス → HTDemucs 4ステム → `analyzeStemsAudio`（製品の高精度モードの再現） |
| C Suno ステム経路 | 9ステムを製品のステム役割へ写像して同じ入口で解析（下記） |
| D 変種 | C の other から FX を除いたもの |

### C の写像と、その理由・限界

製品のステム経路（src/analysis/analyzeStems.ts）がコード判定に使うのは
**mix（キー／テンポ／ゲート参照）・other（コード判定クロマ）・bass
（低域分布）の3つだけ**で、vocals / drums は判定に一切使われない設計
である。したがって写像は:

- bass = Bass
- other = Guitar + Keyboard + Synth + Strings + FX（和声楽器の合算）
- mix = 9ステム合計（= アーム A の入力と同一）
- Vocals / Backing Vocals / Drums は合計ミックス経由でのみ効く

限界: (1) 9ステムの粒度は other 内部では潰れてしまう。楽器別の重み付け
（例: リバーブの多い FX を弱める）は現行アーキテクチャでは表現できない。
(2) Suno のステムも生成時の原素材ではなく完成ステレオへの後付け分離
（サーバー側）であることが公開情報から分かっている。「分離誤差ゼロ」
ではない。(3) C はステムのネイティブな 48kHz で解析した。見出しキー
だけは mix 由来のため 48kHz 異常の影響を受ける（次節）。

## ⚠ 診断: 48kHz 入力でクロマが半音側に回る（アーム A の異常）

アーム A は曲全体を A# マイナー寄りの世界で読み、B/C と全く噛み合わ
なかった。切り分けの結果、**原因は素材でも合計処理でもなく、解析側の
48kHz クロマにある**ことが分かった。証拠:

1. 教科書的な自前 FFT クロマ（8192 点）では、合計ミックスは 48kHz の
まま 05 と回転 0 で cos 0.989（音程は正常）。other / vocals も回転 0
2. プロジェクトのクロマでは、合計ミックスは 48kHz で A# minor、
**同じサンプルを 44.1kHz と仮定すると A minor** に戻る
3. 純正弦波の合成 Am 三和音でも、44.1kHz では A minor（構成音 pc が
正しく上位）だが **48kHz では C# minor と誤読**する（G# が最上位に
混入）。合成 C では 48kHz でも C major だが C# が第2位に混入する
4. 05.mp3 を 48kHz に**正しくリサンプル**した版も A# minor と誤読する
（A# が最長 29 秒）。素材固有の問題ではない

仕組み: プロジェクトのクロマは FFT 4096 点・最近傍ビン割当てのため、
低域ではビン間隔が半音間隔より粗い（48kHz では 110Hz 付近に「A に
丸められるビン中心」が存在せず、A2 のエネルギーが G#/A# のビンに
落ちる）。低域ほど重みを大きくする設計（`1/(1+log2(f/50)*0.35)`）が
この量子化誤差を増幅する。44.1kHz ではビン格子と音名格子の当たりが
偶然良い。誤差の大きさは低域の支配度に比例する: 全帯域ミックス
（低域が強い）で最大、other 単体では軽微、低い合成和音では壊滅的。

**製品への含意（本測定の副産物として最も重要かもしれない）**:
簡易モードはブラウザの `AudioContext` のデコードレート（多くの PC /
Android では 48kHz）をそのまま解析に渡すため、**公開中の簡易モードは
48kHz 環境でこの劣化に晒されている**。高精度モードは分離前に
44.1kHz へリサンプルする設計のため影響を受けない。本書の範囲では
修正しない（測定担当の権限外）が、独立した課題として切り出す価値が
高い。以後、本書の混合音の代表は A44 とし、アーム A の数値は
「48kHz 異常の実例」としてのみ併記する。

## フィクスチャ判定（Q1〜Q4、決着済みの正解に最も近い物差し）

05 の耳チェック照合（SUNO_05_ANALYSIS.md）で決着した読み:
Q1 = 層分離（上層 Am7 系、ベース D、層表示 **C/D**）／ Q2 = **Cm は棄却**
（実態は Am→C の動き）／ Q3 = **C→B7→E7→Am** ／ Q4 = ベース C# 実在・
上層 CM7（層表示 **CM7/C#**）。第2段（7th 判定）は製品既定 OFF のため、
Q3 は三和音レベル（B / E のルート＋メジャー）で判定し、完全ラベルの
7th 有無は対象外とする。

| 窓 | 決着 | B Demucs | C Suno |
|---|---|---|---|
| Q1 0:51–0:56 | ベース D・表示 C/D | 支配 Dm（bass D）・表示 **C/D** ✓ | 支配 Em（bass F#）・表示 Em ✗ |
| Q1 1:33–1:38 | ベース D・表示 C/D | 支配 D（bass D）・表示 **C/D** ✓ | 支配 C（bass D）・表示 C △（ベース正、層表示なし） |
| Q4 1:02–1:05 | ベース C#・表示 CM7/C# | 支配 C#m（bass C#）・表示 **CM7/C#** ✓ | 支配 Em（bass C#）・表示 Em △（ベース正、表示は決着と不一致） |
| Q3 1:25–1:33 | C→B7→E7→Am | 三和音 **4/4** ✓（C / B / E / Am） | 三和音 **4/4** ✓（同） |
| Q2 2:33–2:48 | Cm 棄却、Am→C | Cm **1.05 秒**（小）・小窓 D→C→C | Cm **5.95 秒**・小窓 Cm→C→Cm ✗ |

**フィクスチャでは B が全項目で C と同等以上**。特に層表示の決着
（C/D、CM7/C#）を再現できたのは B だけで、C は Q4 で既知の失敗形
（ベース証拠は拾うが表示が Em に潰れる）になり、Q2 では棄却済みの
Cm を復活させた。C の Q1 前半のベース誤読（F#）は、C の bass が
Suno 純正ステムであるにもかかわらず起きている。

### 帯域の担い手

- **60–120Hz**（SUNO_05_LOWFREQ.md で車載ビリビリの主因とされた帯域）:
Suno では Bass 77.9% + Drums（キック）21.4%。Demucs でも bass
77.3% + drums 21.4% とほぼ同一の配分。低域の担い手判定に両者の
差はない
- **1–4kHz**（ボーカル帯域）: Suno では Vocals 62.3% + Backing 10.1% +
Drums 26.5%（シンバル／スネア自身の帯域）。和声ステム側の保持は
Guitar 0.3% / Keyboard 0.5% / FX 0.2% と小さい。Demucs では
vocals 73.8% / drums 25.6% / other 0.6%。**「ボーカル帯域が和声
ステムへ滲む」量は、どちらの分離でも同程度に小さい**（この代理
指標の範囲では Suno ステムの優位も劣位も測れない）

### 漏れの代理指標（ステム間相関）

- 各ステムと「残り全ステムの合計」との相関は、全セットで |r| ≤ 0.07。
ペア間最大でも Suno 0.044（backing_vocals|keyboard）/ Demucs 0.048
（vocals|other）/ demucs05 0.060（vocals|other）
- 時間領域の相関は、漏れがあっても内容が無相関なら小さく出る鈍い
指標である。この範囲では「どちらかが著しく漏れている」証拠は
得られなかった、とだけ言える

### 「リバーブに溶ける」感の代理指標（ボーカル減衰尾）

- ボーカルステムのオフセット後、包絡が −25dBFS から −55dBFS まで
落ちる時間（中央値）: **Suno 0.83 秒（6 イベント）／ Demucs 0.90 秒
（6 イベント）／ demucs05 0.90 秒（15 イベント）**
- この代理指標では Suno ボーカルの尾が特に長いという結果は出なかった。
イベント数が少なく、MP3 経由でもあり、「溶ける」感の有無をこの
測定で結論することはできない（測れなかった、が正確な記述）

### 合計波形の健全性

- 9ステムの単純合計はピーク 1.257、フルスケール超過 0.0012%
  （割合は小さいが、ピークは +2.0dB 超過する）。配信
ミックスは別途マスタリング（リミット）されたもので、ステムは
プレマスターのゲインで書き出されている。**ステム直接入力の製品
実装では合計時の正規化が必須**という実務的な確認が取れた

## 解釈と限界

- **n=1 の1曲だけの結果**であり、しかも和声ステムが極端に薄い編成の
曲だった。Suno ステム一般への外挿はできない
- C の不利には交絡がある: C は 48kHz で解析しており、低域ビン量子化の
影響を other / bass でも受けうる（B は 44.1kHz 系）。C を 44.1kHz に
リサンプルして再測すれば差の一部は縮む可能性がある（未実施）
- 一致率は「正解率」ではない。B–C 一致率の高さは、両者が同じ判定
パイプライン（s-conditional、同じ other 概念）を共有する構造的な
近さも含む
- 信頼度はテンプレート照合スコアであり、較正済み確率ではない
- MP3 経由のため、ステム品質の細部（高域の滲み、減衰尾）は
ロスレス素材での再測が望ましい

## 所見: Suno ステム直接入力に製品価値はあるか

**精度の面では、少なくともこの曲では「ない」という測定結果だった。**
N.C. 率（C 11.9% vs B 6.9%）、信頼度（0.580 vs 0.635）、フィクスチャ
（決着した層表示 C/D・CM7/C# を再現したのは B のみ、C は棄却済みの
Cm を復活）の全てで Demucs 経路が同等以上だった。「Suno のステムは
粒度が細かいので解析が良くなるはず」という仮説は、この曲の編成
（和声ステムが全体の約4%しかない）では成立しなかった。また現行の
製品アーキテクチャは other / bass / mix しか消費しないため、9ステムの
粒度の大部分はそもそも判定に届いていない。

一方、**ワークフローの価値は実在する**: B の分離にはローカルでも
255 秒かかり、公開アプリ（ONNX）では非力な PC で 20 分超の実績が
ある。ステム直接入力なら分離待ちと 172MB のモデル取得が消える。
「精度で勝てないが、速さと手軽さで意味がある入力経路」という位置
づけなら成立しうる。ただし本測定の範囲では、精度を落としてまで
既定経路にする理由はなく、位置づけは「速い代替入力（精度は Demucs
経路が上限）」が妥当というのが測定に基づく結論である。

そして副産物として、**48kHz クロマ異常の方が製品への影響は大きい**。
これは Suno と無関係に、48kHz でデコードする全ユーザーの簡易モード
に効いている可能性がある問題で、別課題として切り出すことを勧める。

## 追記（2026-10-29）: アーム C の 44.1kHz 再測と解析レート統一

本文の「解釈と限界」で未実施とした交絡切り分けを行った。同日、
48kHz クロマ異常への対策として解析入口で入力を 44.1kHz に統一する
修正が入った（方式 (a)、詳細は CHROMA_48K_FIX.md）。そのため
本追記では C を2通りで再測している:

- **C（修正後）**: 48kHz ステムをそのまま `analyzeStemsAudio` に渡し、
  入口で線形補間リサンプルされる製品の実挙動
- **C44**: bass / other を事前に ffmpeg で 44.1kHz 化してから同じ
  写像で解析したもの（mix は既存の mix44.wav を使用）

両者の一致率はルート 99.4 / 三和音 99.0 / 完全 99.0% で、リサンプラの
違いは読みにほぼ影響しない。以後の「44.1kHz 化した C」の代表は
どちらでも同じだが、数値は C44 を主に引く。

なお、この再測で measurements/suno-yoi-results.json は再生成され、
アーム A / C / D の値は修正後のものに置き換わっている。修正前の値は
本文の各表と git 履歴（コミット 1e326a6 時点）に残っている。アーム
A44 / B は不変性のため完全一致しており、本文の数値はそのまま有効。

### 切り分けの結論

48kHz 要因で説明できたのは、見出しキーの誤り、信頼度の差
（B とほぼ解消）、B との一致率の低さ、Q2 の Cm 時間の約4割である。
一方、**N.C. 率の差（11.3〜11.6% vs B 6.9%）はレート要因を除いても
ほとんど縮まず**、Q1 のベース誤読と Q4 の表示の失敗も残り、
Q1 後半のベースと Q3 の最終スライスはむしろ修正前より悪くなった。

したがって本文の結論は維持される: C の不利の主因はサンプルレート
ではなく、製品のステム経路が mix / other / bass しか消費しない
構造（9ステムの粒度が other 内部で潰れる）と、この曲の和声ステムが
全エネルギーの約4%しかない編成にある。「Suno ステム直接入力の価値は
ワークフローにあり、精度の上限は Demucs 経路」という所見も不変。
