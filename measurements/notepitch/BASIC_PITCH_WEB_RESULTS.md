# Basic Pitch ブラウザ推論の実測（製品化の関門確認）

> 目的: 音符証拠を使う製品機能（音符ベースの判定補助、MIDI 書き出し等）の
> 前提である「ブラウザで Basic Pitch の ONNX モデル（nmp.onnx、230KB）を
> 実用速度で推論できるか」を実測する。ハーネスの準備経緯は
> BASIC_PITCH_WEB_PREP.md、サーバ側の先行検証は NOTEPITCH_VERIFICATION.md。
> 製品コードは無変更。実施 2026-10-29、オーナー承認済み課題。

## 実施方法と、その制約（先に明記する）

- 当初計画は Muse の実ブラウザ（管理対象 Chromium）で測定ページを
  開くことだったが、その自動操作はプライベートアドレスへの移動を
  仕様で拒否し、ユーザーの手動オープンでも開けなかった
- そのため **Playwright 経由のヘッドレス Chromium 156**
  （この VM 上、2 vCPU）で同じハーネスページを実行した。WASM の
  演算エンジンとしては実ブラウザと同一系だが、実機（ユーザーの
  低電力 PC やスマホ）での数字ではない。実機確認は別途必要
- 条件: ONNX Runtime Web 1.31.1（ローカル同梱）、COOP/COEP なしの
  ため **WASM は単一スレッド**。これは現在の公開ホスティング
  （GitHub Pages では同ヘッダを付けられない）と同じ製品実態の条件
- 音源: 合成曲 Song E（18.78 秒、44.1kHz）と、宵のひかり合計ミックス
  先頭 60.08 秒（48kHz）。参照は同一ファイルに対するサーバ側 Python
  推論（実績のある抽出器）の出力
- JS 後処理ポートの正しさは準備段階で先行証明済み（未加工モデル出力に
  対し 170 音全一致、時刻ずれ最大 0.0005 秒）。本書の照合は
  「ブラウザのデコード＋リサンプル＋ORT Web 推論」を通した全体の差

## 結果（WASM、2 回実行の範囲）

| 項目 | Song E (18.78s) | 宵ミックス 60.08s |
|---|---|---|
| 窓数 | 12 | 37 |
| 推論時間 | 2.95–3.31 秒 | 4.28–7.44 秒 |
| 実時間比（推論時間÷音源長） | 0.16–0.18 | 0.07–0.13 |
| 後処理 | 0.45–0.75 秒 | 0.50–0.79 秒 |
| 音符数（ブラウザ／参照） | 171 ／ 170 | 328 ／ 329 |
| 参照イベントの再現（時刻・ピッチ寛容一致） | **170/170（100%）** | 316/329（96%） |
| ピッチクラス別総持続時間の最大差 | 0.11 秒 | 0.30 秒 |

- モデル取得 32ms、WASM セッション生成 約1.8 秒（初回のみ）
- デコード＋リサンプルは 0.4–0.6 秒と軽微
- 1 窓あたり推論は約 120–250ms（初回窓は JIT ウォームアップを含む）。
  3 分半の曲（約128窓）に換算すると、この VM で約 15–35 秒の推論
- 2 回の実行で推論時間にばらつきがある（共用 VM の負荷ゆれ）。
  悪い側でも実時間の 5 倍以上の速度

## 一致度の解釈

- 合成曲は参照を完全再現（寛容一致 100%、追加 1 音のみ）
- 実音源の 96% と差分は、準備報告書が予告したとおり
  **ブラウザ内蔵リサンプラ（48kHz→22050Hz）と librosa/soxr の差**が
  主因とみられる（境界上のイベントの生死が入れ替わる）。
  ORT Web の推論自体の正しさは合成曲で担保されている
- performance.memory はヘッドレス環境で 10MB に量子化固定され、
  ヒープ実測はできなかった（「測れなかった」が正確な記述）。
  ただし窓単位のチャンク処理で完走し、メモリ起因の失敗はなかった

## WebGPU の所見

- 素のヘッドレスでは GPU アダプタがなくセッション生成不可
- `--enable-unsafe-webgpu`（SwiftShader）ではセッションは生成できたが、
  推論が CQT 前段の Mul カーネルで失敗
  （"Can't perform binary op on the given tensors"）
- 少なくとも現行の ORT Web 1.31.1 とこのモデル形状では、WebGPU は
  そのままでは使えない。実 GPU 環境で異なる可能性は残るが、
  **製品経路は WASM 前提で設計すべき**という実務結論（WASM で十分速い）

## 判定

**関門は通過（デスクトップ級ブラウザ、WASM 前提）。**
230KB のモデルが単一スレッド WASM で実時間の 5–14 倍の速度で回り、
出力はサーバ参照と実質一致した。Demucs（172MB・非力な PC で 20 分超）
とは重さの桁が違う。音符証拠の製品機能は「推論できるか」では
もう止まらない。

残る未確認は実機の数字（ユーザーの Linux PC 実ブラウザ、スマホ）で、
特にスマホは Demucs でメモリ落ちした前歴があるため別途の確認が要る。
ただし Basic Pitch は窓処理でメモリが頭打ちになる設計にでき、
リスクは分離より構造的に小さい。
