# 音符レベル解析 検証結果 — クロマ照合 vs 音符証拠ベース推論

実施日: 2026-10-28
位置づけ: 製品実装ではなく、次への投資判断のための実測検証。
仮説: 現行方式（クロマ×テンプレート照合）の主病は倍音混入と「実在の音の
ぼやけ」（7度音の飽和、属音引力）。音高検出で「音符列」に変換してから
コードを推論すれば、テンションは実在音として見え、分数コードは最低音
として解け、精度が上がるはずである。

## 判定基準（事前登録 — 測定前に固定し、後から動かさない）

- **主基準A（合成7th）**: song-e + song-f の完全ラベル正解率（時間加重、
  定義は scripts/extensionScoring.ts と同一: 正解 ext ∈ {maj7, 7, m7,
  なし} の時間について root+mode+ext の完全一致）の平均が、現行最良
  77.8%（Phase 3.1 第2段 ON の stems/合成系記録: Song E 81.9%、
  Song F 73.7% の平均）を **上回れば「有望」**、±3pt 以内
  （74.8〜80.8%）なら **「互角（他の利点で判断）」**、それ未満なら
  **「現方式では不採用」**。
- **主基準B（Suno フィクスチャ）**: SUNO_05_ANALYSIS.md の耳チェック照合
  済み結論との一致を Q1／Q3／Q4 で判定し、**2つ以上一致で合格**。
  - Q1（51–56秒・93–98秒）: ベース層の最低音が D、上層（other）の
    読みが Am7（A+C+E+G の音集合優勢）。両窓とも満たせば一致。
  - Q3（85–93秒、2秒スライス×4）: C → B7 → E7 → Am のうち
    **B7（87–89秒）を含む3スライス以上**が一致すれば一致。
  - Q4（62–65秒）: ベース層の最低音が C#、上層の読みが Am 系
    （Am／Am7／Am(add9)）で、テンション音 B（9th）・G（♭7）が
    実在音符として検出されれば一致（C#m 読みは不一致）。
- **副基準（実曲）**: 曲1（Put Your Records On）stems の triad が
  現行 81.7%（Phase 3.1、s-conditional・第2段 OFF）から **−3pt 以内**
  （≧78.7%）であれば実用域。上回ればなお良い。root も併記する
  （現行 61.4%）。
- 判定は「製品への採用」ではなく「次の投資に値するか」の判定として書く。
  音符検出自体のエラー（検出漏れ・オクターブ誤り・倍音の誤検出）が
  支配的なら、その内訳も示す。

### 比較条件の注記（事前に明記）

- 集計グリッドは Phase 3.1 測定 JSON（phase3-1-*.json）に保存された
  現行システムの検出セグメンテーション（第2段 ON 時）を用い、各検出
  セグメントに音符推論のラベルを1つ割り当てる。採点は extensionScoring
  と同じ 10ms サンプリング・時間加重。したがって境界誤差は現行と
  同条件であり、差分は「証拠と推論」の差として読める。
- 現行の完全ラベル正解率は「検出が N.C. の時間」を分母から除外した値
  （Song E で N.C. 2.9%）。本検証の推論器は常時ラベルを出す（N.C.
  なし）ため分母は全対象時間となり、この点は本検証側に不利な非対称
  として結果の解釈に含める。
- 音符→コード推論のルールと閾値は測定前に固定した（検証スクリプト
  scripts/notepitch/ 参照）。実曲・Suno の結果を見てからの閾値の
  後付け調整はしない。

## 環境と手順（実施記録）

### 音高検出: Basic Pitch は「ONNX 経由」で使用できた

- 素直な `pip install basic-pitch`（0.4.0）はこの環境（Python 3.12）では
  **解決不能**だった。0.4.0 のメタデータが Python ≥3.11 に対して
  `tensorflow>=2.4.1,<2.15.1` を要求するが、TF 2.15 系に cp312 の
  wheel が存在しない。リゾルバが旧版（numpy<1.24 ピン）へ後退すると
  今度は numpy のソースビルドに失敗する。Python 3.11 はシステムに無い。
- 回避策: basic-pitch 本体を `--no-deps` で入れ、パッケージ同梱の
  **ONNX モデル（saved_models/icassp_2022/nmp.onnx、230KB）** を
  onnxruntime で直接使う経路にした。個別に入れた依存は onnxruntime /
  librosa / pretty_midi / mir_eval / resampy / numpy==1.26.4。
  専用 venv は ~/.venvs/notepitch（/tmp は 512MB tmpfs のため不適）。
  推論は CPU で動作した。音声総長 590 秒（合成9曲＋Suno 2ファイル、
  モデル読み込み11回を含む）の抽出に約4.5分。
- フォールバック（手順2）も合成曲のみ参考アームとして実施した:
  単音系は正規化自己相関の F0 追跡、多音系はスペクトルピーク抽出＋
  倍音抑制（scripts/notepitch/extract_fallback.py、numpy/scipy のみ）。
  実曲・Suno の本測定は Basic Pitch で行った（フォールバックは保険
  だったため、実曲では未実施）。

### 推論と採点

- 音符→コード推論は scripts/notepitch/chordinfer.py（ルールは検証前に
  固定。候補 = 12ルート×{長三和音, 短三和音, maj7, m7, dom7}、
  score = explained − 0.10×missing − 0.02×(構成音数−3)）。
- 採点は extensionScoring.ts / measureSynthetic.ts / measureReal.ts の
  定義を Python に移植した。**移植の正確性は検証済み**: 現行システムの
  検出セグメント（第2段 OFF）を自前採点器に通すと、記録値（root /
  triad / 完全ラベル / givenCore）が合成6曲すべてで小数第4位まで
  完全一致した。
- 集計グリッドは事前登録どおり Phase 3.1 の検出セグメンテーション
  （song-a〜f は phase3-1-synthetic の on アーム、song-g〜i は
  phase3-genre-synthetic の off アーム、実曲は phase3-1-real-stems の
  stemsOn）。加えて診断用に「正解グリッドで集計した参考値」
  （truthGrid）も併記する。これは主判定には使わず、境界汚染と推論
  誤りの切り分け専用である。
- 実曲の音符推論は bass rule v1 のコードで実行した（実曲の指標は
  ベースを同点タイブレークにしか使わないため影響は無視できる）。
  Suno フィクスチャは v1 の欠陥判明後に v2 でも再測定した（後述）。

| Song B（対照） | 87.8 | 87.8 | **53.5** | — | **46.2%** | 86.4 |
| Song C（対照） | 97.2 | 97.2 | **97.2** | — | 0.0% | 91.9 |

- **主基準A: Song E+F の完全ラベル平均 = 76.6%**（現行最良 77.8%、
  差 −1.2pt）→ 事前登録の **「互角（74.8〜80.8%）」** 帯域。
  内訳は E が −2.4pt、F が ±0（偶然にも完全一致）。
- Song D（分数コード、混合音）は現行 18.6% → **66.4%** と大幅改善。
  ベース音の正解率（正解グリッド）は全曲 **100%** で、「分数コードは
  最低音として解ける」という仮説の主張は合成では完全に支持された。
- Song B の崩壊は誤発火が原因（Am→Am7 が 4.41 秒、C→Cmaj7 等）。
  三和音曲でも倍音由来のゴースト7th音符が share 0.03〜0.08 で実在し、
  素朴な「7th があれば拡張」判定を反転させる。Phase 3.1 の maj7
  問題が、音符証拠でも形を変えて残ることの実証（後述のエラー内訳）。
- Song H は A7→Am7（4.26 秒）等の dom7/m7 モード混同が中心。
  隣接する D7 の C♮ が境界を跨いで混入するパターン。

**参考（正解グリッド集計 = 推論層だけの天井）**: 完全ラベルは
Song A/C/E/F/H/I が **100%**、B/D が 87.5%、G が 100%。
givenCore は E/F/H とも 100%。つまり検出セグメンテーションが
正しければ、音符証拠＋この単純な推論ルールで 7th 曲はほぼ完全に
解ける。検出グリッドとの差（E: 79.5→100、F: 73.7→100、
H: 66.1→100）は全て境界汚染である。

**フォールバック（参考アーム、合成のみ）**: 完全ラベルは E 76.3 /
F 79.7（平均 **78.0**、BP と同水準）、H 82.7、I 88.6 と健闘したが、
Song D は 12.8% に崩壊（低音のピーク取りこぼし）。軽量な独自実装
でも合成レベルでは BP に迫れることの示唆。

### Suno 05 フィクスチャ（主基準B）

ベース規則 v1（「最大重みの0.3倍以上を持つ最も低い音高」）では
Q1・Q4 ともベースを取り違えて不合格だった。内訳を見ると、検出器の
支配的なベース音高そのものは全窓で正しかった（Q1b: D2 が重み 1.32 で
首位、Q4: C#2 が 1.03 で首位）。敗因は v1 規則が「より低いゴースト／
経過音（重み約半分）」を優先する欠陥だったため、規則を v2
（ピッチクラス合算の argmax。プロジェクト既存の
aggregateBassDistribution と同じ統計）に修正して再測定した。
**判定基準自体は動かしていない。**

| 窓 | v2 の読み | 登録した照合結論 | 判定 |
|---|---|---|---|
| Q1（51–56） | **Cmaj7/D**（bass D ✓） | Am7/D | 不一致 |
| Q1（93–98） | **C/D**（bass D ✓） | Am7/D | 不一致 |
| Q3（85–93） | Cmaj7 → **B7** → C#m7/E → Am7 | C → B7 → E7 → Am | **一致**（B7 含む3/4） |
| Q4（62–65） | **Cmaj7/C#**（bass C# ✓、B・G は実在音符として検出 ✓） | Am系/C# | 不一致 |

- **主基準B: 1/3 一致 → 事前登録どおり不合格。**
- ただし実質の読みは注目に値する。Q1・Q4 の音符読みは、SUNO_05_ANALYSIS
  の当初の照合（Am7 系）ではなく、**Phase 3.2 が層表示の実測で改訂した
  結論（Q1=C/D、Q4=CM7/C#）と正確に一致**した。音符証拠でも A
  （Am のルート）の share は 0.083／0.038 と薄く、B（CM7 の長7度）は
  実在音符として立つ。2つの独立した証拠系統（クロマ層分析と音符列）が
  同じ改訂結論に収束したことになる。
- Q3 の E7 スライスは C#m7 とスコア差 0.01 の惜敗（E7 の構成音合計
  0.793 対 C#m7 の 0.803。ゴーストの C# 0.076・A# 0.078 が差を作った）。
  ベースは v2 で E と正しく読めている（C#m7/E）。
- Q4 のテンション音 B（9th）・G（♭7）は音符として実在検出できた。
  「テンションは実在音として見える」という仮説の核心は実音源でも
  支持された（読みの帰属先が Am でなく CM7 だっただけである）。

## エラー内訳（支配要因の切り分け）

1. **検出器（合成曲ではほぼ無罪）**: Basic Pitch のピッチクラス
  レコールは全曲 1.00（正解の構成音は全セグメントで検出）、
  非構成音の証拠 share は 0.2〜1.3%（Song G のみ 5.6%）。
  ベース音高の支配音は Suno の全フィクスチャ窓でも正しかった。
  → 合成レベルでは「音符化の情報損失」は誤差の主因ではない。
2. **セグメンテーション境界（合成での最大要因）**: 検出グリッドと
  正解グリッドの差が完全ラベルで最大 34pt（Song H）。境界の前後
  0.2〜0.5 秒の隣接コード音符の混入が、7th の取り違え（G7→Gm7、
  A7→Am7）と三和音への未発火の主因だった。
3. **7th ゲート（残存する古典的問題）**: 倍音ゴースト音符は share
  0.03〜0.08 で実在するため、「実在すれば拡張」とは即断できない。
  正解グリッドでも Song B/D に誤発火 12.5% が残る。Phase 3.1 の
  結論（7th は文脈と二段構えで扱う）は音符証拠でも維持される。
  ただし規模は縮小した: クロマ時代の「証拠が飽和して原理的に
  分離不能」から、「閾値と持続時間で扱える問題」に変わった。
4. **推論の素朴さ（実曲での最大要因）**: 全音符を一様に数えるため、
  旋律線・リード楽器・装飾音が和音証拠を汚染し、相対短調への
  系統誤読を生む。持続音の重み付け、オンセット集中度の割引、
  帯域（低音＝ルート、高音＝モード）のような現行の知見の音符版が
  要る。
5. **ベース規則 v1 の欠陥（修正済み）**: 「最も低い支配音」は
  低音ゴーストに弱い。ピッチクラス合算の argmax（v2）が正しく、
  これは既存の低域クロマ集計と同じ統計だった。

## 結論（次の投資に値するか）

事前登録した判定は、主基準A「互角」、主基準B「不合格（1/3）」、
副基準「不合格」。**この形のまま（現行セグメンテーション＋素朴な
全音符推論で推論器を置き換える）では採用しない。**

しかし内訳は仮説の核心を支持している:

- 音符証拠は 7th・テンション・分数コードの判定に**十分な情報を
  含む**（正解グリッドで完全ラベル 100%、分数コード曲で +47.8pt、
  ベース 100%、Suno の層結論を独立に再現）。
- 解けていないのは証拠の「組み立て」であり、課題は特定できた:
  (1) セグメンテーションを音符オンセット／和声変化で作る
  （最大のレバー。境界が揃えば合成 7th はほぼ解ける）、
  (2) 推論に持続音重みと帯域の役割分担を入れる（実曲の旋律線
  汚染への対処）、(3) 7th は音符証拠でも文脈との二段構えを維持。
- 判定文言としては「**音符レベル化は次の投資に値する。ただし
  投資先は推論器の置換ではなく、セグメンテーションと証拠選別を
  含む再設計である**」とする。

### 次への申し送り

- セグメンテーション再設計（音符オンセット駆動）が最優先の検証
  テーマ。今回の音符列キャッシュ（measurements/notepitch/notes/）は
  そのまま再利用できる。
- 推論 v2 の論点: 音符の持続時間と振幅だけでなく「和音らしい
  同時性」（ストラム的な同時発音のクラスタ）を重みに入れる、
  7th は持続する実在音符のみを証拠にする（短いゴーストの除外）。
- 製品化の論点は別途: Basic Pitch の ONNX モデルは 230KB と小さく
  ONNX Runtime Web と同系統だが、CPU 推論は実時間の約0.5倍
  （2コア実測）で、ブラウザ WASM では更に遅くなる見込み。
  フォールバック級の軽量ピーク抽出でも合成では BP に迫ったため、
  「軽量な独自音符化＋賢い推論」も設計空間に残る。ライセンスと
  実ブラウザ速度の確認は製品化判断の前に必要。
- 再現: `python3 scripts/notepitch/run_verification.py --engine bp`
  （音符キャッシュ利用時は抽出を省略。--bass-rule v2 で Suno の
  修正規則版、--engine fallback で参考アーム）。
  生データ: notepitch-results.json（v1）/
  notepitch-results-v2bass.json（v2＋正解グリッド参考値）/
  notepitch-results-fallback.json。
