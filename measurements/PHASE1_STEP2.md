# Phase 1 Step 2 測定結果 — 分数コード（スラッシュコード）対応

測定日: 2026-10-28 / ハーネス: scripts/measurePhase1Step2.ts（`npm run measure:phase1-step2` で再実行可能）

## 実施内容

- `scripts/synth.ts`: 進行の各コードに `bassPc`（ルートと別のベース音）を
  指定できるよう拡張。正解 JSON の各セグメントにも `bass` / `bassPc` を
  ルートとは別フィールドで記録するようにした（A–C はベース=ルートで不変）。
- `src/lib/chordDisplay.ts`（新規）: 表示名を組み立てる純粋関数
  `displayChordName(chord, bassPc)`。ベース=ルートなら通常表示、
  ベースが 3rd / 5th の構成音なら分数表示（C/E 等）、構成音でなければ
  通常表示のまま。React UI（タイムライン／一覧／再生中のコード）、
  テキスト譜の書き出しに適用。JSON 書き出しは chord と bass を
  別フィールドのまま保持し、分数表記は保存しない。
- `src/analysis/bassCorrection.ts`: Step 1 の補正が分数コードを壊さないよう
  ゲートを追加。ベース音が検出コードの構成音の場合は分数コードの可能性が
  高いため、候補コード（ルート=ベース音）のクロマスコアが検出コードの
  スコア − 0.08 以内の場合に限って補正する。それ以外はルートを変えず
  bassPc だけを残す。構成音でないベース音は従来通り補正する。

  ゲートの実測根拠（合成 4 曲、候補スコア − 検出スコア）:
  補正が必要な相対調ケース（Am → C ×5件）は −0.041 以上、
  補正してはいけない分数ケース（C/E、F/A 等）は −0.144 以下だったため、
  ほぼ中間の 0.08 をしきい値に採用した。

## 制限と所見

- Song D の誤りの中心は分数表示以前の Phase 0 のルート誤りである。
  ベースが構成音を強く鳴らす条件では、そのピッチクラスが全帯域クロマを
  引っ張り、ルート自体の検出が崩れやすい（例: Am/E の小節が Dm と検出される）。
  分数表示は「ルートが正しく検出できたセグメント」でのみ効く仕組みであり、
  このクラスは Phase 2（ステム分離でベースとコード楽器を分けて見る）の
  改善対象と考える。
- ベース音が構成音でない場合は、設計通り分数表示にせず通常表示のままに
  している（Step 1 のルート補正の領域であり、表示側では新挙動を作らない）。
- ゲートのしきい値（0.08）は合成 4 曲の実測に基づく。実曲のベースは
  もっと曖昧なため、Step 3（実曲測定）で再確認が必要。
- 合成音源はベースが拍頭で明快な条件であり、数字は上限値として読むこと。
  Phase 1 の完了判定は Step 3（実曲 3 曲の測定）を経てから行う。
