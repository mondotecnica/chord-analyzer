# Theory Engine 第1段: 候補リストの露出 — 実装と検証

作成日: 2026-10-29
位置づけ: THEORY_ENGINE_DESIGN.md §7 の第1段（§2 前提の補強）。認識エンジン
本体は無変更で、確定セグメントへの加算的な出力追加のみ。製品既定は
変えていない（露出は明示オプトイン `candidateRecord`、既定 OFF）。
数値の一次資料: theory-step1-results.json（本ディレクトリ、
`npm run measure:theory-step1` で再生成可能）。

## 1. 実装内容

- 新モジュール `src/analysis/candidates.ts`: 確定セグメント列を受け取り、
  セグメントごとに上位 k 候補を `ChordSegment.candidates`
  （`SegmentCandidate[]`、src/types.ts）として付ける純粋な後段処理。
- 接続点: 混合音経路（analyze.ts）とステム経路（analyzeStems.ts）の
  両方で、全ての判定・後段処理（拡張音検出まで）が終わった直後に
  1 か所ずつ。`analyzeStemsAudio` には省略可能な第3引数 `opts` を
  追加した（既存の呼び出しは無変更で従来動作）。
- オプション（既存の記録系フラグの流儀に倣う）:
  - `candidateRecord?: boolean`（既定 false、明示オプトイン）
  - `candidateCount?: number`（k の指定。1〜24 にクランプ）
- JSON／テキスト書き出しへの候補の追加は行っていない（今回の範囲外。
  書き出しは製品判断が別途必要）。

## 2. 候補の定義

候補は三和音コア（12 ルート × major/minor = 24 通り）の列であり、
各候補は (root, mode, bassPc, score, margin) を持つ。

- **1位は確定ラベルで固定する**（構成による）。root / mode は
  セグメントの `chord` の解釈、bassPc はセグメントの `bassPc` そのもの。
- **スコアの定義**: 「そのセグメントの集約証拠が実際に付けたスコア」
  として、コード判定用クロマ（上帯域 chordFrames）のセグメント区間
  エネルギー加重平均と各テンプレートのコサイン類似度
  （bassCorrection.ts の `chordChromaScore` をそのまま使用）を全候補で
  共通に使う。別設定での再計算はしていない（使うクロマとエネルギーは
  その実行でパイプラインが実際に使ったもの）。
  - この集計を選んだ根拠: 既定経路で最後に (root, mode) を決める
    「モード決め直し」（splitBand.ts）と、第2段（拡張音検出）が
    証拠に使うのと同じ集計であること。実装前のプローブ実測では、
    この集計で「確定ルート内で確定モードが argmax」になる率が
    全スイート（合成 A〜I／実曲 1〜3／Suno 05、両経路）で **100%**
    だった。つまり同ルートの代替候補が勝者を上回ることは構造的に
    起きない。
  - 一方、確定ラベルが単一集計の全体 argmax になる率は低く
    （上帯域集計: 合成 85.0%／実曲混合音 41.5%／実曲ステム 48.7%、
    全帯域集計でも実曲 46.3%／52.5%）、確定ルートはフレーム列の
    投票とベース証拠（低域分布）を含む複合判定であって、単一の
    クロマ集計では再現できない。だからこそ 1位は構成で固定し、
    スコアは「この集計が付けた値」を正直に併記する形にした。
- **マージン**: 1位のスコア − その候補のスコア（1位自身は 0）。
  異ルートの代替候補は上帯域集計だけで見れば勝者を上回ることが
  あり、その場合マージンは**負**になる。符号を潰さず保持する:
  「この集計だけなら代替が勝っていた。確定はフレーム列／ベース
  証拠に依る」という情報は、第2段のタイブレーカー判定（設計書 §5）
  が必要とする信号そのものであるため。
- **順序**: 1位（確定ラベル）の後に、代替候補を集計スコア降順で
  並べる（同点はテンプレート順＝ルート昇順、同ルートは major →
  minor で決定的に解く）。
- **bassPc は全候補で共通**: ベース音は候補の属性ではなく
  セグメントの証拠（低域分布）として確定済みのため。候補が
  格上げされた場合の表示名は、候補の (root, mode) とこの bassPc
  から消費側が組み立てる。
- **候補空間に含めないもの**: 拡張音（maj7 / 7 / m7）と上層候補
  （upperChord / upperExtension）。拡張音は第2段の内部語彙であり、
  その露出は別段の課題（§7 引き継ぎ事項）。上層候補は設計書 §8 で
  未決のため第1段では含めず、層表示は従来どおりセグメントの
  フィールドとして保持される。

### k の扱い

- 内部既定は **k=5**（オプション `candidateCount` で変更可能）。
  根拠は §4 のオラクル被覆率: k=3 → 5 の伸びはまだ有意にあるが、
  候補列の消費側（系列最適化）の計算量と監査可能性を考えると、
  まず 5 を既定として第2段の較正で見直すのが妥当、という判断。
  被覆率そのものは k=1,2,3,5 で測ってあるため、既定値の再判断は
  数字から可能。

### N.C. セグメントの扱い

- 確定状態は N.C. のまま変えない。候補には「ゲートで棄却された
  対抗候補」の上位 k を、同じ集計スコアで載せる（1位 = 最有力の
  棄却候補、マージンはその候補基準で非負・降順）。
- 設計書 §3 のとおり系列最適化は N.C. を候補列上の状態として
  含み、§6.5 のとおり評価器は N.C. にラベルを発明しない。
  この候補列は「鳴っていたら何だったか」の記録であり、N.C. 状態
  そのものはセグメント側が担う、という役割分担である。

### ステム経路との差異（無理に揃えていない点）

- 定義の形（集計→コサイン、1位固定、符号つきマージン）は両経路で
  同じだが、集計の中身が違う。混合音経路は混合音の chordFrames、
  ステム経路は **other ステムの chordFrames** であり、後者は
  「分離された和声ステムだけの証拠」である（ベース／ドラム／
  ボーカルを含まない）。ステム経路ではベース証拠は bass ステムの
  低域分布から確定ラベルと bassPc にのみ入り、候補スコアには
  入らない、という非対称も混合音経路と同じ構造である。
- ステム経路の層の再読（layerChord）は other の全帯域クロマを使う
  が、候補の集計はモード決め直し・拡張検出と揃えて上帯域にした。
  これは意図的な選択であり、差異としてここに明記する。

## 3. 事前登録基準（実施前に転記した検証基準と、その判定）

以下は実装着手前に本書へ転記した基準であり、この基準で判定した。

1. **不変性**: 露出 OFF/ON の両条件で、全既存スイート（合成 A〜I の
   混合音・ステム、実曲 1〜3、Suno 05 両経路、宵のひかり各アーム）の
   結果が現行 HEAD とビット一致すること。48kHz 修正時と同様、
   測定ツリーの再帰 diff で証明する
2. **整合性**: 露出された候補の 1位が、そのセグメントの確定ラベルと
   常に対象ごとに一致すること（層表示や分数コードの構成要素を含む）。
   一致しないケースがあれば、それは候補定義の誤りとして扱い原因を
   特定する
3. **回帰**: 全テスト合格。新規テストで候補の順序性（スコア降順、
   マージン非負）、1位＝確定ラベルの一致、N.C. の扱いを固定する

### 判定

**基準1（不変性）: 合格。** 2つの方法で証明した。
- ハーネス内の直接比較: 全 22 スイート（合成 A〜I 混合音、実曲 1〜3 の
  両経路、Song D ステム、Suno 05 両経路、宵のひかり 4 アーム
  A44／B／C／C44）で、candidateRecord OFF/ON の判定結果（キー・BPM・
  全セグメントのラベル構成要素・信頼度）が完全一致した。
- 全スイート再実行＋測定ツリーの再帰 diff: 既存の測定ファイルに
  測定値の差分は無かった。差分として現れたのは (a) ハーネスが
  実行日を刻む「測定日」行のみが変わる MD 4 件（差分が行単位で
  日付行だけであることを確認済み。測定値ではない）、(b) 新規追加の
  measurements/theory/ のみ。なお suno-yoi-results.json の診断項目
  1 件は手作業で事前作成する /tmp/05-48k.wav の有無に依存する
  環境依存項目であり、同ファイルを用意した条件では差分は出ない。

**基準2（整合性）: 合格。** ハーネスの整合性検査（22 スイートの
全セグメント）で違反 **0 件**。1位候補は常に対象セグメントの確定
ラベル（root / mode / bassPc）と一致し、マージンは定義どおり
（1位 = 0、各候補 = 1位スコアとの差）、代替候補はスコア降順、
N.C. セグメントの候補は棄却候補列として形状を満たした。
一致しないケースは無かったため、候補定義の誤りとしての原因特定は
発生しなかった。

**基準3（回帰）: 合格（ただし文面との差異を 1 点明記する）。**
全テスト合格（従来 413 件＋1 スキップ → 新規の単体テスト 9 件と
本ハーネス 1 件を追加）。新規テストで固定した性質は次のとおり:
1位＝確定ラベルの一致（層表示・分数コードの構成要素を含む）、
代替候補のスコア降順とマージン定義、N.C. の扱い、OFF で候補が
付かないこと、ON でも両経路の判定が完全一致すること。
- 差異の明記: 基準文面の「マージン非負」は、同ルートの代替候補に
  ついては構造的に保証される（§2 の実測 100%）が、異ルートの代替
  候補については**意図的に符号つきマージンを採用した**ため、
  全候補についての非負は成り立たない。これは基準の緩和ではなく
  設計判断である: プローブ実測のとおり、単一の集計スコアでは
  確定ラベルが argmax になる率が実曲で 4〜5 割しかなく、
  「1位＝確定ラベル」「正直な実スコア」「マージン非負」は
  同時に満たせない。負のマージンは「上帯域集計だけなら代替が
  勝っていた」という、第2段の較正に必要な情報を保持するための
  選択であり、テストでは符号つきであること自体を固定した。

## 4. オラクル被覆率（副次測定）

**これは再評価器が到達可能な上限（天井）の測定であり、精度改善の
主張ではない。** 「正解が候補列の中にいる」ことと「第2段がそれを
正しく選べる」ことは別であり、後者は第2段の測定で初めて分かる。
また k=1 の値は定義上、現行パイプラインの正解率そのものである
（本ハーネスの標本規約: 0.05 秒標本、検出がラベルありの時間を
分母とする labeled 基準）。

実曲 1〜3 の正解は再構成による**近似**である（手作業で検証した
正解ではない）。合成 A〜I は完全な正解。Suno はフィクスチャ
範囲のみ。

## 5. 第2段への引き継ぎ事項

### 5.1 候補列の消費上の注意（第1段の実測から）

- 候補スコアは較正された確率ではなく、テンプレート照合の
  コサイン類似度である（既存の confidence と同じ性質）。設計書 §5 の
  対数線形合成では、音響スコアのスケールとしてそのまま扱わず、
  マージン（差）の方を主信号にするのが安全である。
- マージンの符号の意味: 同ルート代替のマージンは常に非負で、
  モード軸の接戦度をそのまま表す。異ルート代替の負マージンは
  「上帯域集計だけなら代替優位（確定はフレーム列／ベース証拠）」を
  表す。タイブレーカー閾値（§5）はこの符号つきマージンで較正する
  こと。
- N.C. の候補列は棄却候補であり、格上げ対象ではない（設計書
  §6.5）。Q2 窓の実測（§4）が示すとおり、棄却された読みは候補内に
  高率で残存する。
- k の再判断材料: 被覆の伸びは合成では k=2 でほぼ飽和するが、
  実曲では k=5 まで伸び続ける（混合音 triad: k=3 48.8 → k=5 61.4）。
  系列最適化の計算量と相談し、第2段の較正で決めること。
- bassPc と候補ルートの不一致を一律に減点しないこと。層表示の
  実測（Phase 3.2）と下記 5.3 のルートレスボイシングの観点から、
  「ベース≠ルート」は異常ではなく様式的な通常形でありうる。

### 5.2 拡張段の候補露出が別途必要（オーナー補足: 様式 prior は語彙・命名にもかかる）

オーナーの具体イメージ（2026-10-29 補足）: 様式 prior は進行統計
だけでなく、**拡張音の語彙・命名の選択**にもかかる。同じ C 系統でも
AOR なら Cmaj9、Jazz なら Cmaj13、シティポップなら Cmaj7、
ロックなら C のような「ありがちな形」を候補として加味する。
この実現には、第1段（三和音コアの候補列）とは別に、拡張段
（第2段判定）の候補空間とスコアの露出が必要になる見通しである。
現行の拡張検出（extensionDetection.ts）が内部に持つ形状は
次のとおり:

- **仮説空間の形**: 24 テンプレート型のランキングではない。
  セグメントあたり最大 3 仮説だけを評価する —
  (a) 検出ルートのままの maj7（major のみ）、
  (b) dom7（major）／m7（minor）、
  (c) ハイジャック再解釈（検出ルートが全音上の dom7 の 7 度音
  だったという仮説。bassPc が再解釈先ルートと一致する場合のみ）。
- **証拠の形**: `SegmentEvidence { shares[12], persistence[12] }`。
  shares は上帯域クロマのセグメント平均のピッチクラスシェア
  （L1、両端 12% トリム）、persistence はピッチクラスごとの
  持続性（シェアが床以上のフレーム割合）。
- **候補ごとに内部計算される量（現在は破棄され、最終判定
  `{extension?, rootOverride?}` だけが返る）**: 三和音テンプレート
  適合 fit3、各候補の 4 音テンプレート適合 fit とその改善
  fit − fit3、7 度音のシェア（生値／音符証人の差し替え後／maj7 の
  背景割り引き後の shareForTest）、実際に適用されたしきい値
  （ダイアトニック緩和 ×0.9、ジャンル係数、クラス別床の合成）、
  持続性、棄却（veto）や抑制の発生有無。露出する場合は
  judgeExtension の返り値へ候補レコード列を加える形が、第1段と
  同じ加算的流儀として自然である。
- **語彙の制約**: 現行語彙は maj7 / 7 / m7 のみで、**maj9 / maj13 は
  表現できない**。9 度（root+2）・13 度（root+9）のシェア証拠自体は
  shares[12] の中に含まれているが、テンプレートも閾値も存在しない。
  様式パック側の命名選択（Cmaj9 vs Cmaj13 のような読み分け）を
  実装するには、拡張段の語彙拡張（9/13 を含むテンプレートと
  閾値の較正）が前提になる。
- **既存の土台**: `bestTemplateCandidate(shares)` が 12 ルート ×
  {三和音 major/minor, maj7, 7, m7} の全テンプレート適合を返す
  （現在は層の再読専用）。拡張候補の露出を作る際の土台になる。
- **様式の出所の制約（既存の制約をそのまま適用）**: 様式 prior は
  対象曲自身の認識結果から推定しない（フィードバックループ禁止、
  設計書 §6.2）。進行統計と同じく、外部の様式パックまたは利用者の
  選択が独立した情報源になる。語彙・命名の prior もこの制約の
  下に置く。

### 5.3 演奏実践の層（オーナー補足第2弾）

オーナーの構想では、様式 prior は次の 3 層にかかる:

1. **和声文法**（進行・機能関係）— 設計書 §1 の 5 軸そのもの。
2. **語彙・命名**（拡張音の選択）— §5.2 のとおり。
3. **演奏実践由来の音響特徴**: 楽器ごとの特徴的なボイシング
   （エレピ／アコピ／オルガン等）があり、低域でオープンボイシングに
   しないと濁る等、その演奏上の特徴が生む周波数特性（ボイシングの
   音域配置・音程間隔、楽器固有の減衰／持続特性）まで判断材料に
   できるのではないか、という層。

引き継ぎとしての整理:
- (3) は記号レベルの prior（(1)(2)）と違い、**信号特徴として
  実装・測定できる**反面、「どの楽器が鳴っているか」の**楽器同定が
  前提部品になる**見通しである（ボイシングの特徴は楽器条件つきで
  あるため）。楽器同定は本プロジェクトで未着手の部品であり、
  第2段の範囲には含めず、将来の前提としてここに記録する。
- 既存知見との接点: ジャズの**ルートレスボイシング**は
  「ベース≠ルート」事案の説明になる — 鍵盤側がルートを弾かず
  ベースがルートを担う（あるいはその逆の読み替えが起きる）ため、
  層表示・分数コードの読み（Phase 3.2）と候補の bassPc の解釈に
  直接関係する。第2段の設計では、bassPc と候補ルートの不一致を
  様式によっては通常形として扱える余地を残すこと（§5.1 の注意と
  同じ結論を、演奏実践の側からも裏付ける）。
