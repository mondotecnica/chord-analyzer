## 設計（実装の要約。詳細は src/analysis/genreProfile.ts の冒頭コメント）

### 部品の置き場

- 新規モジュール `src/analysis/genreProfile.ts`。局所キー
  （localKey.ts）と同じ形の小さな部品で、共有プロファイル
  （第1段セグメント列・全体キー・局所キーと同じ解析成果物）を
  読むだけで、判定器とは独立にジャンル傾向＝様式プロファイルを
  推定する。
- 結果は `AnalysisResult.genreProfile` に相加的に格納し、表示
  （結果サマリ1行）と書き出し（JSON／テキスト）に出す。
  将来の他用途（分離調整・MIDI 変換・マスタリング基準、
  DESIGN_NOTES の想定）はこのフィールドを読む形で接続できる。
- 記録と消費の分離（3.3 分割採用と同じ規律）:
  - `genreRecord`（既定 true）= 推定＋格納＋表示のみ。ラベル不変。
  - `genre`（既定 false）= 消費部。第2段（extensions 有効時）に
    ジャンル文脈として渡るのはここだけ。

### ユーザーの設計入力（2026-10-28、実装中に提示）で変わったこと

当初案は「和声特徴だけから単一のジャンルラベルを推定する
分類器」に近い形だった。実装中にユーザーから次の設計観が
提示され、設計は3点変わった（却下した部分はない）:

1. **判定要素は音楽の三大要素（リズム／メロディ／コード）が
   基本** → 特徴量を「和声／リズム／メロディ／音色」の
   チャンネル構成に再編した（次節）。当初は和声チャンネル
   しかなかった。
2. **ジャンルは歴史的に人の移動と地元様式の混合で形成される
   ことが多く、単一ラベルでなく混合パーセンテージを
   読み取れないか** → 出力を「様式ファミリーへの混合比率
   （分布）」そのものにした。表示も混合のまま（% 併記）で
   見せ、下流の prior も比率で重み付けした混合として効く
   （比率は装飾ではなく機能する）。当初案でも分布は内部的
   には持っていたが、top を主役にする設計だった。
3. **正直さの境界（助手側の線引きとして明示）**: この % は
   「特徴空間における様式プロトタイプへの類似度」であって、
   **文化的系譜そのものの比率ではない**。どの土地の伝統が
   何割受け継がれたかは音響特徴からは原理的に測れない。
   したがって名称は「様式プロファイル（推定）」とし、
   系譜の比率と誤読される表現はコード・表示・文書の
   どこにも使わない。

### 特徴量のチャンネル構成

- **和声**（常に実在）: 第1段セグメント列＋第2段と同じ証拠
  クロマから計算。7th 音プレゼンス3種（maj7／dom7／m7）、
  ダイアトニック時間割合、二次ドミナント形の時間割合、
  5度下行遷移の割合、短調コード割合、分数コード割合、
  ♭VII 時間割合、使用コード種数。遷移系（5度下行・
  二次ドミナント・変化率）は同一コードの連続セグメントを
  畳んだ「ラン」を単位にする（第1段のセグメントは小節内で
  割れることが多く、生の境界では遷移の実態が断片化に埋もれる。
  較正時の実測で判明）。♭VII は長調キーでのみ測る（短調では
  VII はダイアトニックそのもので借用の印にならない）。
- **リズム**: オンセット包絡の密度と拍の規則性（自己相関
  ピーク。検出 BPM の絶対値には依存しない）、和声リズム
  としてのコード変化率。ステム経路ではドラムステムの包絡を
  優先する。検出 BPM 自体は倍取り・3:2 取り違えが実測されて
  いるため特徴量に入れない。
- **メロディ**: ボーカルステムがある場合のみ。ボーカル
  クロマのスケール適合度（全体キーのスケール音にある質量の
  割合）とコードトーン比率（その時点のコード構成音にある
  質量の割合）。混合音経路では分離されていないため測れず、
  チャンネルは欠落として記録される（無いものをあるように
  見せない）。
- **音色**: 4ステムが揃う場合のみ、ステム RMS シェア。
  混合音経路では欠落。なおアプリの高精度モード入口は現状
  drums／vocals を解析層へ渡していないため、アプリ経由では
  メロディ／音色は欠落になる（測定ハーネスは4ステムを渡す。
  アプリ側の配線は将来の拡張点として残す）。

新規チャンネル（リズムの包絡系・メロディ・音色）の傾向は
識別力が未検証のため、広い σ と小さい重みで「弱く効く」
置き方にし、効きの評価は本書の測定結果で行う。

### 推定方法（傾向表スコアリング。学習済み分類器ではない）

- 分類体系は5つの広い様式ファミリー: jazz / blues / soul /
  pop / rock。選定理由: 本プロジェクトの検証コーパス（実曲
  3曲＝ソウル寄りポップ／J-Pop バラード／ロック、合成の
  ジャズ循環・ブルース・♭VII ロック、ユーザーの Suno 自作曲
  ＝ポップ系）が実際に跨ぐ範囲であり、これ以上細かい体系
  （サブジャンル等）は今の特徴量では裏付けが取れない。
  細分化は将来の課題として明記する。
- スコアリングは「様式ごとの傾向（中心 μ と広がり σ）」に
  対するガウス類似度の重み付き平均 → softmax で混合比率に
  する。傾向表は音楽学的な常識（例: ブルースでは I／IV にも
  dom7 が常套、ロックでは ♭VII 借用と三和音主体、ジャズでは
  ii–V–I と全種の 7th が常套）に基づいて手で置いた値であり、
  学習データは存在しない。欠落チャンネルの特徴量は全様式で
  除外し、重みを正規化し直す（材料が減るだけになる）。
- 定数（μ／σ／重み／softmax 温度）の較正は合成曲（A–I）と
  Suno フィクスチャの範囲でのみ行う。実曲 1–3 は検証専用で、
  較正には使わない（3.1／3.3 と同じ規律）。較正に使った範囲と
  調整の経緯は本書の「調整の経緯」に残す。

### 消費部（第2段への効かせ方）

- スタイル分布 × スタイル別「拡張クラス親和度」（下表）の加重
  平均で、曲単位の maj7／dom7／m7 親和度を出す。
- judgeExtension では、候補クラスのシェアしきい値に
  `factor = clamp(1.11 − 0.23 × 親和度, 0.88, 1.11)` を掛ける。
  既存のダイアトニック緩和（×0.9）と同じ桁の柔らかい prior で、
  候補の除外は一切しない（§2）。+11% の上限は、スタイル推定が
  外れても強い証拠を prior が潰し切らないための保険。
- 背景シェア割り引き（3.3）はセグメント局所の統計であり、
  ジャンル prior は曲単位の統計である点が違う。3.3 の失敗分析
  （真の maj7 と誤発火は局所統計では分離不能）に対し、曲全体の
  語彙傾向という別の軸を持ち込むのが本モジュールの狙い。

| スタイル | maj7 | dom7 | m7 | 根拠（常識レベルの傾向） |
|---|---|---|---|---|
| jazz | 1.00 | 1.00 | 1.00 | 全種の 7th がトニックでも常套 |
| blues | 0.15 | 1.00 | 0.60 | dom7 が I／IV の色そのもの。maj7 は稀 |
| soul | 0.85 | 0.70 | 0.90 | maj7／m7 のトニック色付けが常套 |
| pop | 0.45 | 0.55 | 0.60 | 7th は V7 と vi の m7 が中心 |
| rock | 0.10 | 0.40 | 0.35 | 三和音主体。maj7 は稀、7th は V 中心 |

### 基準ごとの判定

**基準1（妥当性）: 不合格。**
合成9曲は全て登録した集合内（E／F=jazz、H=blues、I=pop、
A–C=pop、G=soul、D=pop）。しかし実曲は混合音で3曲とも
top=jazz（登録集合 {pop, soul, rock} の外）、ステムでも曲1が
jazz 83%。原因は特徴量側にある: 実音源では上帯域クロマの
7 度音プレゼンスが合成曲より大幅に高く出る（倍音の重なりで
「7th らしい」証拠が飽和する。ext アームが曲1／2のステムで
28.7 秒／71.8 秒もの maj7 を許可していること自体がその現れ）。
傾向表の較正は規律どおり合成曲のみで行ったため、実音源の
プレゼンス分布の違いを吸収できていない。曲1（ソウル寄り
ポップ）が jazz 83% と出るのは表示としても誤解を招く水準。

**基準2（守り）: extG は合格、extG33 は文面どおりには不合格
（ただしジャンル起因ではない）。**
extG のルート／三和音／コアは混合音・ステム全曲で ext と
完全一致（差 0.0pt）。合成9曲のルート／三和音も ext と完全
一致。extG33 は曲2ステムのコアが ext 比 −0.8pt（0.199 vs
0.207）で 0.5pt の幅を超えたが、その値は ext33 と完全一致
しており、低下分は 3.3 で既知の局所キー消費部の小さな低下
そのもので、ジャンルの純効果は 0。

**基準3（曲3ステムの maj7）: 決定的に不合格。**
extG: maj7 合計 63.7 秒（物差し ≤ 8.7 秒）、GM7 38.0 秒、
完全ラベル 0.200（物差し ≥ 0.467、ext の 0.273 すら下回る）。
extG33 でも 15.1 秒／完全ラベル 0.442 で ext33（8.7 秒／
0.467）に届かない。仕組みは明確: 曲3のプロファイルが
soul 47%＋jazz 26% と「7th の多い様式」に寄る（基準1の
飽和がここでも効く）→ maj7 親和度 ≈ 0.72 → 係数 ≈ 0.94 と
ゲートが緩む → 誤発火が増える。**プロファイルは、それが
再重み付けするのと同じ 7th 証拠から推定されており、独立した
情報になっていない（フィードバックループ）**。3.3 で残った
「文脈 prior が要る」という課題に対し、少なくともこの形の
ジャンル prior は答えにならなかった。

**基準4（曲1／2ステムの givenCore）: extG は合格。**
extG の2曲平均 0.897（曲1 0.947、曲2 0.847）は物差し
0.791（ext 平均 −5）と 0.730（ext33 平均 +5）の両方を上回り、
ext 平均 0.841 自体も超えた。7th が実際に密な曲では、様式
文脈が真の 7th を取り戻す方向に働いた。ただし代償も同時に出て
いる: 誤発火率 曲1 0.171→0.211、曲2 0.529→0.612、maj7 合計
曲1 28.7→35.0 秒、曲2 71.8→97.4 秒、完全ラベルは曲1
0.574→0.588（+1.4pt）・曲2 0.173→0.171（−0.2pt）とほぼ横ばい。
つまり「真の 7th と誤発火の分離」が改善したのではなく、
閾値の動作点が緩い側へ移動しただけであり、3.3 の分離不能
という結論は覆っていない。extG33 の平均は 0.735 で
0.730 の物差しを辛うじて上回るが 0.791 には届かない。

**基準5（Suno フィクスチャ）: 登録文面どおりには不合格。
ただしジャンル起因の変化はゼロ。**
extG の Q3 は合格（ext と同じ）。しかし Q1 の pass は false、
Q2 の stage2Pass も false で、登録した「合格」の文面を満たさ
ない。切り分けると、この2つの false は ext アーム（＝3.1 の
条件）でも同一であり、phase3-1-suno.json の記録とも一致する
既存の状態（Q1 は窓の支配的セグメントが Dm7/D でフィクスチャ
定義上の合格形と違う、Q2 は窓内の Cm に m7 が付くため
stage2Pass が false）。extG のフィクスチャ結果オブジェクトは
ext と完全一致（Q1 はオブジェクト等価、Q2 の Cm 秒数も
4.75 秒／1.1 秒で不変）で、ジャンルは Suno のどこにも新しい
誤りを生んでいない。なお extG33 では Q2 strictPass が true
（Cm 0 秒、3.3 の ext33 と同挙動）、Q3 も合格。

**基準6（合成の第2段）: 合格。**
Song E 完全ラベル extG 0.819（物差し ≥ 0.799）、Song F 0.737
（≥ 0.717）、Song H 0.650（ext と同値）、Song I の誤発火率
全アーム 0。副次的な観察として、合成曲ではジャンル文脈が
第2段の判定を1件も変えなかった（全アームで完全ラベルが
完全一致）。合成曲の判定はゲート境界から遠く、係数 ±0.11
では動かないということであり、ジャンル prior の効きは
実音源の境界事例でのみ現れる。

**基準7（記録のラベル不変性）: 合格。**
19 スイート（合成9、実曲 混合音4＋ステム4、Suno 両モード）
で、アプリ既定（記録 ON）と genreRecord: false のセグメント
タプル＋キー＋BPM が完全一致（差分総数 0）。全既定ランで
genreProfile が記録されていたことも同時に確認した。

### 経路別の消費部まとめ（参考）

混合音経路では extG の完全ラベルが3曲とも ext を下回った
（曲1 0.426→0.369、曲2 0.130→0.110、曲3 0.185→0.106）。
混合音のプロファイルは3曲とも jazz top で、緩和方向の係数が
誤発火を増やした（誤発火率 曲3 0.526→0.775 等）。消費部を
仮に使うとしても混合音経路は対象外にすべき水準。

## 調整の経緯

- 較正プローブ（合成9曲のみ、実曲不使用）での反復:
  (1) 初期案では Song C（短調の三和音曲）が rock 寄りに

## 判定と採用提案

**消費部（`genre`）: 採用しない（既定 OFF のまま据え置き）。**
登録した採用条件（基準2–6 の全合格）を満たさず、とりわけ
基準3（曲3の GM7 誤発火）がジャンル文脈で悪化したことが
決定的。3.3 の時点で「maj7 の真陽性と誤発火は現特徴量では
分離不能」と分かっていた課題に対し、本モジュールの prior は
独立情報を持ち込めなかった（プロファイル自体が同じ 7th
証拠の飽和に引っ張られる）。第2段（extensions）自体の既定
OFF も従来どおり変更しない。

**記録・表示部（`genreRecord` 既定 ON）: 分割採用を提案する
（3.3 の局所キーと同じ形）。** 基準7（ラベル不変性）が
19 スイート完全一致で合格しており、コードへの影響なしに
様式プロファイルを結果画面と書き出しに残せる。ただし基準1
の失敗があるため、表示は現行の「混合比率を % で併記し、
単一ラベルを断定しない」形を維持することが採用の条件になる
（jazz 83% のような表示は、それが「特徴空間での類似度」で
ある但し書きとセットで初めて正直になる。書き出し JSON には
特徴量とチャンネルの有無も含めてあり、後から検証できる）。
公開（push）は本ラウンドでは行わず、ユーザーの承認を待つ。

**将来への申し送り（今回は実装しない）:**
- 実音源でのプレゼンス較正: 合成と実音源で 7 度音プレゼンスの
  分布が違うことが基準1失敗の主因。実音源側の分布に合わせた
  μ の置き直しは、較正に実曲を使うことになるため、別の検証
  曲を用意してからでないと規律（実曲＝検証専用）を崩す。
- 消費の非対称化・確信度ゲート: プロファイルの margin が
  小さい曲では消費しない、係数を緩和方向（< 1.0）に使わない、
  等の設計は基準3の失敗様式への直接の対処になるが、事前登録
  の範囲外の再設計であり、やるなら新しい事前登録から始める。
- アプリの高精度モード入口は drums／vocals を解析層へ渡して
  いないため、アプリ経由ではメロディ／音色チャンネルが欠落
  する。配線すれば表示の材料が増える（消費とは無関係）。

これで Phase 3 の計画項目（3.1／3.2／3.3／後半ジャンル）は
全て実施・測定済みになる。残る未着手は PHASE3_PLAN.md §5 の
拍子・小節推定モジュール（追加提案・未承認）のみ。
