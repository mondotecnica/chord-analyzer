## 作ったもの

### 表現（型と伝播）

- `ChordSegment` に相加的フィールドを追加（src/types.ts）:
  `upperChord?: string`（上層の三和音コア）、`upperExtension?:
  ChordExtension`（上層の 7th）、`addTones?: ("add9")[]`。
  いずれも未設定＝従来表現と完全互換。
- ベース補正（src/analysis/bassCorrection.ts）: 強いベース証拠で
  ルートを潰す補正が発火したとき、潰される前の和声側の読みを
  `upperChord` に記録する。それ以外の挙動は不変。
- conditional（src/analysis/conditionalBand.ts）: 自分が書き換えた
  セグメントについて、新しい候補が upperChord と一致する場合のみ
  層フィールドを保持し、食い違えば落とす。
- ユーザーがセグメントを手動修正したら層フィールドも消す
  （src/App.tsx の editSegment）。

### 上層の再読 src/analysis/layerChord.ts（新規）

保持した読みが常に正しいとは限らない（ベース補正が治した相対調の
取り違えでは、フレーム側の読みこそ誤り）。そこで upperChord を
持つセグメントだけを対象に、セグメント集計証拠で「層が実在するか」
を判定し、実在する場合のみ上層を再読する。chord / extension /
bassPc / 境界には一切触れない。

- 証拠帯域は経路で分ける。混合音経路は**上帯域クロマ**
  （chordFrames）: 混合音の全帯域クロマは低域の FFT ビン分解能
  不足でベース基音が ±1 半音へ滲み（実測: 合成の Am/E 小節で
  F=0.238 / D=0.185 の幻影。Goertzel で原音自体は A/C/E のみと
  確認）、テンプレート適合が歪むため。ステム経路は **other
  ステムの全帯域クロマ**: 分離後の other の低域は実在のルート
  情報を含み（STEM_BAND_AB の知見）、Q4 の C/A の証拠は other の
  低域側にあって上帯域では拾えないため。
- 再読候補は三和音24テンプレート＋第2段と同じ 7th 語彙
  （maj7 / 7 / m7）の最良適合（extensionDetection の
  bestTemplateCandidate を流用）。ベース音のピッチクラスは
  証拠から 0 にして集計する。候補のルートがベース音と一致する
  場合は採用しない（上層は定義上ベース音をルートに持たない）。
  7th 候補には床を課す: maj7 は再読専用の床 0.14（Song D の
  G メジャー小節で 3 度音 B の3倍音が F# として 0.122 観測され
  第2段の床 0.10 では GM7 と誤読した。真の maj7 である Q4 の
  B は 0.158〜0.166）、その他は第2段と同じ床＋持続性＋
  三和音からの適合度改善。
- 置き換えは、保持済み読みの適合度を 0.005 以上上回る場合のみ。
- **層の実在ゲート**: 次のいずれかなら層を落とし、表示は
  補正後コードに戻る。(a) 補正後コードの三和音適合度 > 0.65
  （補正後の読みで十分説明できる＝相対調の取り違えだった形）。
  (b) 表示される上層の適合度 − 補正後コードの「7th 込み」
  適合度 < 0.06。(c) 証拠がベース音ルートのコードを表示上層
  より 0.06 超強く支持する。較正点: Q1 の補正後 Dm は三和音
  適合 0.216 / 0.333、Dm7 込みでも 0.523 / 0.563 に対し上層 C は
  0.969 / 0.932 で余裕を持って通過。Q4 は C#m7 込みとの差
  0.096 で通過、誤った層の実例（Q3 解決部で Am の ♭7 である
  G が上層に立つケース）は差 0.054 で棄却。**0.06 の床は
  0.054 と 0.096 の間にあり、境界近傍の分離である**ことを
  明記する。

### add9 付加音 src/analysis/addToneDetection.ts（新規）

拡張 ON のときだけ、第2段の直後に走る。対象コードは上層
（upperChord があればそちら、無ければ chord）。7th 拡張が
付いている音は 9th であって add9 ではないので対象外。
9th 音がベース音そのものの場合はベース層の音として数えない。
0.5 秒未満のセグメントは前後の滲みで汚染されやすいため対象外
（実例: Q3 の 0.38 秒の C セグメントに次区間の影響で add9 が
誤って付いた）。

- 床は分布の実測で決めた（合成全曲のセグメントで 9th 音の
  シェア／持続性を集計）: 三和音対照の生シェアは最大 **0.094**
  （5 度音の3倍音が 9th として現れる幻影の床）、Song G の真の
  add9 はストラムを含むセグメントで **0.135〜0.195**、
  アルペジオだけのセグメントでは **0.049〜0.052** まで落ちて
  幻影の床と分離できない（測定上の限界、下記）。床は 0.11。
- 実曲では生シェアだけでは誤発火が多発した（AHDN stems 拡張で
  Cadd9 / Dadd9 が約14件）。other ステムにはメロディラインが
  含まれ、9th 音はメロディとして頻出するため。3.3 の maj7
  文脈 prior と同じ考え方で背景シェア（その音が構成音でない
  他区間でのシェア中央値）を係数 0.5 で割り引く併用により、
  AHDN の add9 誤発火は 14 件 → 3 件に減り、Song G の真陽性は
  すべて維持された。

### 表示と書き出し

- 表示は src/lib/chordDisplay.ts の `displaySegmentChord` が
  一元的に組み立てる（再生表示・セグメント一覧・タイムライン・
  テキスト書き出しが共用）。層がある場合: 上層の完全名
  （upperChord＋upperExtension、add9 があれば付加）に、ベースが
  上層ルートと異なれば `/ベース` を付ける。ベースが上層の
  構成音かどうかは問わない（ベース証拠の強さは upperChord の
  存在自体が担保する）。層が無い場合は従来規則（Phase 1:
  構成音ベースのみ分数表示）と完全一致する。
- add9 の表記は慣行に従い、メジャーは `Cadd9`、マイナーは
  `Am(add9)`。
- JSON 書き出しは upperChord / upperExtension / addTones を
  ある場合だけ相加的に含む。テキスト書き出しは層表示を使う。

## 表記の判断（Q1: Am7/D ではなく C/D）

計画の回帰目標は「Q1 = Am7/D（または D9sus4 相当）」だった。
照合時の Am7 という読みは**窓レベルの集計**（前後の Am 区間を
含む）から得たものだが、今回セグメント単位で測り直すと、
当該セグメントの上層証拠は C メジャー三和音が適合 0.93〜0.97 で
支配的であり、Am は隣接区間の混入だった。したがって 3.2 の
表示は `C/D` になる。C 三和音＋ベース D の音集合 {C, E, G, D} は
D9sus4（D G C E、5 度音 A を欠く形）と同一であり、計画の
「D9sus4 相当」の許容形に当たる。耳コピーの Am7 は上層の
Am7/D としての同定だったが、音響証拠の側は C/D を支持する、
というのが正直な記録である（Q4 は計画の許容形 CM7/C# で一致）。

## 限界（正直な記録）

1. **層ゲートの境界近傍性**: minFitGap 0.06 は、誤った層の
   実例 0.054 と真の層 Q4 の 0.096 の間にある。較正点が
   2 点しかなく、余裕は小さい。新しい曲で境界を跨ぐケースは
   ありうる。
2. **add9 のアルペジオ盲点**: 9th 音がアルペジオで疎にしか
   鳴らない場合、そのシェア（≈0.05）は 5 度音の3倍音という
   幻影の床（≈0.09）と分離できない。add9 検出は「9th が
   まとまって鳴っている」場合に限って働く。
3. **同一音集合の区別不能**（計画 §3.2 の原理的限界の再確認）:
   C6 と Am7、Dmaj7 系と F#m/D のような組は音だけでは
   区別できず、テンプレート適合でも同点になる。文脈での
   最終判断は人間に残る。
4. **第1段の誤りは治らない**: 層表示は表現であり、モード
   取り違えや相対調の混乱そのものは第1段／3.3 の守備範囲。
   Q2 窓の Cm はその実例。
